# NeuralFX-ETS2

Version 4.1.1 is a DXGI proxy for D3D11 post-processing in Euro Truck Simulator 2 and American Truck Simulator. It applies screen-space reflections and approximate indirect lighting to the game's SDR image using a captured depth buffer, followed by photorealistic grading, the included LUTs, and RCAS sharpening. The 4.1 minor series adds Steam screenshot integration. Version 4.1.0 failed in-game on both Windows and Proton because it skipped games with an existing screenshot handler. Version 4.1.1 intercepts the game's screenshot callback and captures the final processed frame. The user confirmed that F12 screenshots and ETS2 photo-mode captures retain the plugin effects in 4.1.1. ATS and the remaining platform checks still need verification.

## Building on Windows

Requirements: Windows x64, Visual Studio 2022 with Desktop development with C++, the Windows SDK, and CMake 3.24 or newer. Run these commands in Developer PowerShell:

```powershell
cmake -S . -B build -A x64
cmake --build build --config Release
ctest --test-dir build -C Release --output-on-failure
cmake --build build --config Release --target neuralfx_package
```

The expected output is `build/Release/dxgi.dll` alongside the `build/Release/NeuralFX` folder. By default, the installation package is written to `dist/FSR-ets2-ats-4.1.1.zip`, using `project(... VERSION ...)` in CMake. Shaders are compiled at runtime during initialization to make testing easier. The DLL uses x64 MASM to preserve the arguments of exports forwarded to Windows DXGI.

Before installing, validate the exports on the same Windows system with `powershell -ExecutionPolicy Bypass -File tools/check-exports.ps1 build/Release/dxgi.dll`. If the script fails, the DLL is not ready for that system.

## Cross-compiling on Linux

With Zig 0.16, Ninja, and CMake, run these scripts from the repository root. The build script compiles the project; the package script builds it and creates the installation ZIP:

```sh
./scripts/build.sh
./scripts/package.sh
```

Pass the desired `major.minor.patch` or `vmajor.minor.patch` version to `package.sh`. It writes `dist/FSR-ets2-ats-<version>.zip` and prints the full path. Without an argument, it uses the project version from CMake. The output is `build/windows-x64/dxgi.dll` with supporting files in `build/windows-x64/NeuralFX`. This build was compiled as PE x64, passed the proxy smoke test in Wine, and ran in ETS2 1.61.1.1 via Proton with the ray tracing mode enabled.

## Installation

Back up any existing `dxgi.dll` in the executable directory before installing. Copy `dxgi.dll` and the `NeuralFX` folder together into the directory containing `eurotrucks2.exe`, usually `bin/win_x64` within the ETS2 installation. Do not replace Windows DXGI or modify the game executable. The `NeuralFX/logs/neuralfx.log` file in that directory confirms that the plugin loaded.

The distributed `NeuralFX/neuralfx.ini` uses:

```ini
enabled=true
mode=raytracing
photoreal_sharpness=0.30
lut_strength=0.5
lut_path=luts/neuralfx-ets2.cube
```

The package includes `NeuralFX/luts/neuralfx-ets2.cube`, `NeuralFX/luts/neuralfx-ets2-profile-2.cube`, and `NeuralFX/luts/neuralfx-ats.cube`. The ETS2 LUT is generated by this project. To use the second ETS2 profile, set `lut_path=luts/neuralfx-ets2-profile-2.cube` in the INI; to use the ATS LUT, set `lut_path=luts/neuralfx-ats.cube`.

`mode=hook` tests forwarding only; `copy` performs a GPU copy round trip; `fullscreen` runs the copy pass; `rcas` applies sharpening; and `photoreal` runs grading, RCAS, and finishing. `mode=raytracing` adds screen-space reflections and approximate indirect lighting from the game's color and depth buffers before the photoreal, LUT, and RCAS passes. It can only use geometry visible in the depth buffer; if the buffer is unavailable, it falls back to the photoreal pipeline. `sharpness` accepts values from 0 to 1 in `rcas` mode; `photoreal_sharpness` controls RCAS in `photoreal` and `raytracing` modes. Changing `mode` requires restarting the game.

In `photoreal` and `raytracing` modes, the backbuffer is copied before `Present`. Ray tracing adds a screen-space pass before color processing. The color pass writes sRGB to an `R16G16B16A16_FLOAT` intermediate target; the finishing pass applies RCAS, grain, and dither to the backbuffer. The `exposure_ev`, `contrast`, `saturation`, `clarity`, `highlight_boost`, `highlight_warmth`, `shadow_coolness`, `neural_strength`, `black_level`, `lut_strength`, `grain_strength`, `tone_strength`, `highlight_start`, `highlight_end`, and `photoreal_sharpness` parameters, and every `rt_*` key, can be changed in the INI while the game is running; the plugin reloads them within one second. The initial `photoreal_sharpness` value is 0.30. `lut_path` points to a 3D `.cube` LUT with a 0-to-1 domain and a size from 2 to 64, relative to the `NeuralFX` folder. The LUT is optional and is applied only when `lut_strength` is greater than zero. The neural residual is optional and is applied only when a producer supplies an SRV to the renderer and `neural_strength` is greater than zero; this version does not include such a producer.

## Screen-space ray tracing

The `raytracing` pass converts the captured depth to view-space distance, reconstructs positions and normals from neighboring pixels, and works in linear color. Reflections march a 3D ray projected onto the screen, refine the hit, and weight it with Schlick Fresnel; they apply only to upward-facing surfaces, fade near the screen border, and reflect sky pixels that an upward ray reaches. Ambient occlusion and one bounce of indirect light come from visible geometry within `rt_occlusion_radius`. Sampling uses per-pixel noise that stays fixed between frames, so the pattern does not flicker. The pass writes linear color to the `R16G16B16A16_FLOAT` intermediate target, and the photoreal pass reads it without decoding again.

| Key | Default | Range | Meaning |
| --- | --- | --- | --- |
| `rt_reflection_strength` | 0.30 | 0–1 | Reflection blend after Fresnel and masks |
| `rt_occlusion_strength` | 0.30 | 0–1 | Ambient occlusion darkening |
| `rt_bounce_strength` | 0.25 | 0–1 | Indirect light from nearby occluders |
| `rt_occlusion_radius` | 1.5 | 0.1–10 | Occlusion search radius in meters |
| `rt_thickness` | 0.5 | 0.01–10 | Assumed surface thickness for reflection hits, in meters |
| `rt_max_distance` | 250 | 1–10000 | Distance in meters beyond which pixels are left unchanged; also the reflection ray length |
| `rt_near_plane` | 0.1 | 0.001–10 | Game camera near plane |
| `rt_far_plane` | 5000 | 1–1000000, at least twice the near plane | Game camera far plane |
| `rt_vertical_fov` | 55 | 10–150 | Game vertical field of view in degrees |
| `rt_depth` | `standard` | `standard`, `reversed` | Depth convention; `reversed` treats 0 as far |
| `rt_debug` | `off` | `off`, `depth`, `normals`, `occlusion`, `reflection` | Shows one stage directly on screen, bypassing grading |

The projection defaults (`rt_near_plane`, `rt_far_plane`, `rt_vertical_fov`, `rt_depth`) are estimates that have not been validated in ETS2 or ATS. Calibrate them in game: with `rt_debug=depth`, distance should form a smooth gradient from black near the camera to white at `rt_max_distance`; with `rt_debug=normals`, flat ground should look light green and surfaces facing the camera olive. A wrong `rt_depth` makes the sky dark in the depth view. The log records `Screen-space depth copies per frame: N` whenever the count changes; values above 1 mean the game unbinds several full-resolution depth targets per frame, and the pass uses the last one.

## GPU scene ray tracer

`src/raytracing` is a triangle ray tracer for scenes supplied by code. It runs on the GPU through a D3D11 `cs_5_0` compute shader (`shaders/scene_tracer.hlsl`). The CPU only validates the scene and builds the bounding volume hierarchy. D3D11 has no hardware acceleration structures, so `pack_scene` converts the hierarchy, triangles, materials, and directional lights into structured buffers. `GpuRaytracer` uploads those buffers and dispatches one thread per pixel. Each thread traverses the hierarchy with a 40-entry stack, computes ambient and Lambert lighting with hard shadow rays, and follows mirror reflections for up to 16 bounces. `render` reads the result back into an `Image` that `write_ppm` can save. The hierarchy splits at the median, so its depth stays within the traversal stack for any 32-bit triangle count. The tracer is not part of the game pipeline because the plugin has no access to the game's scene geometry. Its tests use a hardware or WARP device and compare hierarchy traversal with a single-leaf brute-force traversal.

## Steam screenshots

The screenshot key remains configured and handled by Steam (F12 by default). NeuralFX intercepts the game's imported callback registration during DLL attachment. It relays the game's existing `ScreenshotRequested_t` handler to final-frame capture only after the renderer and Steam API are ready. When the game has no existing handler, NeuralFX registers its own and enables `HookScreenshots(true)`. Manual callback dispatch and existing handlers that could not be intercepted remain unsupported. The plugin uses the game's callback loop and does not call `SteamAPI_Init`, `SteamAPI_Shutdown`, or `SteamAPI_RunCallbacks` itself.

Handlers registered after activation are also intercepted. NeuralFX delegates each request once and preserves the game's hook when that handler becomes available.

A request waits for an eligible frame. NeuralFX reads the final backbuffer after all active passes, converts its RGBA/BGRA pixels to 24-bit RGB, and calls `WriteScreenshot` before forwarding `Present`. GPU readback occurs only for pending requests. With `enabled=false` or `mode=hook`, it submits the original game frame. If capture or submission fails, the integration restores the previous handler and logs the failure. The game's original hook state and callback unregistering remain intact. Steam writes the library entry asynchronously.

After a failure, the consumed request and remaining queued requests are reissued through `TriggerScreenshot` after restoring the previous handler. The game's callback loop or Steam Overlay handles these requests. If the Steam API is unavailable, the inability to reissue them is logged explicitly.

The supported screenshot path uses single-sample, 8-bit RGBA/BGRA UNORM or SRGB backbuffers. Successful interception, activation, submission, and completion are recorded in `NeuralFX/logs/neuralfx.log`. The integration test verifies one processed capture when a game already hooks screenshots; it uses a simulated Steam API and does not replace real Steam validation.

The user confirmed that F12 screenshots and photo-mode captures in ETS2 retain the plugin effects in 4.1.1. The successful report did not specify Windows or Proton. Remaining manual checks include ATS, the platform matrix, one library entry per request, matching `ScreenshotReady success` logs, disabled effects, multiple requests, resolution changes, fullscreen/windowed changes, and Alt+Tab.

## Resource trace diagnostics

The resource trace records how the game builds a frame, as evidence for locating the scene color before the HUD, depth, motion-vector candidates, and the render resolution. Create an empty file named `capture-trace` in the `NeuralFX` folder while the game is running, in any `mode`. Within one second, the plugin deletes the file, logs `Trace capture requested`, and records the next two complete frames into `NeuralFX/logs/neuralfx.log`. Create the file again for another capture.

Each frame is written between `Trace frame begin` and `Trace frame end`. Entries list, in order, render-target bindings (`pass`, with `rt=` color targets, `ds=` depth, the first viewport, the draw count, and `reads=` for pixel-shader inputs that are render or depth targets, including targets written in earlier frames), copies and resolves involving those targets, and color and depth clears. `bb` is the swapchain back buffer. `Trace target` lines summarize every target with its size, DXGI format number, sample count, writes, and reads. Draws issued by NeuralFX itself during `Present` are not recorded. A target with `writes=0` was read before being written in the traced frame, which identifies history from a previous frame.

Passes that write `bb` also list each draw (`draw`, with the vertex or index count, the pixel shader, and the render-target `inputs=` bound at that draw), up to 256 per frame, which separates the scene copy from HUD draws. At the first draw of each pass that binds a depth target, including shadow maps and reduced render scales, `constants vs` lines record the vertex constant buffers bound in slots 0 to 3, with the bound byte `offset=` and `size=` and up to 64 float values copied back from the GPU at that draw; `values=unknown` means the copy failed. Each copy waits for the GPU, so captured frames take longer. Comparing these values between the two captured frames shows camera and projection changes such as jitter.

The draw, copy, clear, viewport, pixel-shader, and shader-resource hooks are installed only after the first capture request. Each frame keeps at most 4096 entries; the `dropped=` count reports any excess. Compute dispatches, pixel-shader constant buffers, and deferred contexts are not traced.

## Motion vector diagnostics

The motion probe checks the temporal inputs that an upscaler needs, without changing the game image except for a debug inset. Create an empty file named `motion-debug` in the `NeuralFX` folder while the game is running; within one second the plugin deletes it and logs `Motion probe enabled`. Create the file again to turn the probe off.

While enabled, the plugin recognizes the scene passes by their render targets: the geometry pass (four or more color targets sharing the size of its depth target, which gives the render resolution), the lighting pass (two color targets on that depth), and the game's temporal anti-aliasing resolve (two color targets at the render resolution without depth). At the first lighting draw it copies 32 floats from the vertex constant buffer in slot 0, the camera view and the jittered view-projection, into a GPU buffer. A compute pass derives the projection, the subpixel jitter, and the reprojection from the current to the previous frame on the GPU, so `Present` never waits for the camera. Camera motion vectors are then reconstructed from the scene depth, in render pixels from the current to the previous position.

The CPU does not need the camera of the current frame. In Euro Truck Simulator 2 the jitter follows a 16-frame R2 low-discrepancy sequence, so the plugin predicts it from the frame count. A copy of the camera is read back without waiting a few frames later and checked against the prediction: a match keeps the prediction, a mismatch restarts the sequence and the history, and a jitter outside the sequence stops the prediction until a known jitter appears again. A camera copy whose projection is not a jittered perspective is rejected and logged as `Motion camera rejected frame=M reason=...` with the bottom row of the projection and its jitter terms; the reasons are `singular-view`, `not-perspective`, `jitter-out-of-range` and `empty-size`. A rejected copy also stops the prediction and restarts the history, because the camera of the frames in flight cannot be trusted. A copy whose jitter is valid but outside the sequence is logged as `Motion camera unmatched frame=M jitter=x,y view=... view_projection=...` with both matrices. Consecutive copies also give the camera movement between frames: when the camera moves more than 2 m or turns more than 20 degrees in one frame, the plugin logs `Motion camera jump frame=M move_m=... turn_deg=... from=x,y,z to=x,y,z` and restarts the history. Since the copies arrive a few frames late, the restart also comes a few frames after the cut.

The top-left quarter of the screen shows the motion vectors: gray means no motion, more red means motion to the right, more green means motion downward. The first 240 frames after enabling are logged as `Motion frame N status=... render=WxH jitter=x,y sync=result@M cpu_us=...`. `ready` frames have valid motion vectors; `first-frame`, `resized` and `camera-cut` restart the history; `unsynced` means the jitter phase is not known yet or was lost; `no-jitter` means the game's temporal anti-aliasing is off, so frames carry no jitter; `no-scene` and `no-camera` mean the passes or the camera constants were not recognized. `sync` appears when a delayed camera copy arrives and tells whether it `confirmed` the predicted jitter, `resynced` the sequence, or was `lost`, with `M` the frame the copy came from. `cpu_us` is the CPU time the probe spent on the frame. Every 240 frames a `Motion summary` line counts ready frames, camera cuts, synchronization results, rejected copies and camera jumps, and reports the largest CPU time, the largest movement and turn between consecutive frames, and the largest camera distance from the world origin. Each session of the probe logs at most 32 rejection, 32 unmatched and 32 jump lines.

The probe also copies, without waiting for the GPU, the pixel shader constants of the game's temporal anti-aliasing resolve every frame. Its jitter (in pixels) and the relative camera transform between consecutive frames are decoded from them. The summary reports `resolves` (decoded copies), `resolve_matched` (jitter inside the 16-phase sequence), `resolve_rejected` (copies whose layout or size did not match) and the largest movement and turn per frame (`max_resolve_move_m`, `max_resolve_turn_deg`). A `Motion resolve frame=N jitter=x,y phase=P move_m=... turn_deg=...` line is logged for frames that move at least 0.05 m, turn at least 0.5 degrees or whose jitter is outside the sequence (`phase=none`), and `Motion resolve rejected frame=N reason=...` for rejected copies, at most 32 lines of each kind.

While the probe is on, creating an empty file named `constants-debug` in the `NeuralFX` folder logs the vertex and pixel shader constant buffers (slots 0 to 7, up to 256 floats each) bound at the first draw of the lighting pass and of the temporal anti-aliasing resolve, for the next 4 frames, as `Pass constants frame=N pass=lighting|resolve stage=vs|ps slot=S buffer=... offset=... size=... first=F values=...`, 32 values per line. Reading the buffers waits for the GPU, so those frames take longer.

The motion vectors describe only camera movement; vehicles and other objects that move on their own are not represented. The GPU uses single precision, so the error grows with the camera distance from the world origin: for surfaces 0.3 m from the camera it stays below 0.01 px within about 50 m of the origin and reaches about 0.2 px at 4.7 km, where the single-precision camera matrices themselves already limit the result to about 0.09 px.

## Verified scope and limitations

- The plugin reads the already composed backbuffer, so post-processing also affects the HUD. The code accepts only 8-bit RGBA/BGRA backbuffer formats. For `_SRGB` formats, the SRV decodes and the RTV encodes sRGB in hardware. For `_UNORM` formats, the shader assumes sRGB-encoded SDR values, decodes them for grading, and writes encoded values after RCAS. The actual ETS2 color space still needs validation through a frame capture.
- HDR10 and scRGB are outside the supported path because their backbuffer formats are rejected during initialization. The image is left unchanged in those modes. The game already applies its own tone mapping before this hook, so the filmic tone mapper is blended subtly using `tone_strength`, initially 0.20.
- Input and output resolutions are the same. EASU is disabled until a lower-resolution scene color target can be identified reliably and the HUD can be separated. This version does not provide FSR1 upscaling.
- The plugin captures a depth target for screen-space ray tracing. There is no DirectML/ONNX, overlay, F9 capture, G-buffer detection, motion vectors, or temporal upscaling. Sharpening implements the core RCAS equations in HLSL, with numerical safeguards at the edges.
- The hooks cover swapchains created by factories obtained through `CreateDXGIFactory`, `CreateDXGIFactory1`, and `CreateDXGIFactory2`. Swapchain creation and depth capture were observed in ETS2 1.61.1.1 via Proton.
- The proxy forwards DXGI calls by name or by the original ordinal at runtime. It provides ordinal forwarding slots 1 through 40; the Windows DXGI observed during development uses slots 1 through 20. Run `tools/check-exports.ps1` against the target Windows installation before use. Systems with ordinals above 40 are unsupported. The startup fix in version 3.0.4 was validated in ETS2 on native Windows; the new screenshot feature has separate manual checks.

## Step-by-step validation in ETS2

Start with `mode=hook`, then try `copy`, `fullscreen`, and `rcas`. In each mode, check initialization, resolution changes, Alt+Tab, switching between fullscreen and windowed modes, and shutdown. Confirm swapchain detection, resolution, and GPU cost in the log. If renderer initialization fails, the pass is disabled and `Present` is forwarded to the original DXGI. Keep the effect disabled to obtain a visual reference.
